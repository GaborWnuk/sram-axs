# Releasing

`@gaborwnuk/axs-core` is published to npm **by hand**. Automating it would mean
keeping an npm automation token in repository secrets and rotating it every 90
days; a long-lived publish credential is a larger liability than the saved
keystroke is worth.

Tagging is still automated: pushing a `v*` tag runs
[`.github/workflows/release.yml`](.github/workflows/release.yml), which re-runs
the full check, packs the tarball and creates the GitHub release. That workflow
needs no secrets.

## Steps

1. **Bump the version.** The tag and `package.json` must agree — the release
   workflow refuses to run if they do not.

   ```sh
   npm version minor --workspace=@gaborwnuk/axs-core   # or patch / major
   ```

2. **Verify locally.** This is the same gate CI applies.

   ```sh
   npm run check
   ```

3. **Inspect what would ship.** `files` is an allowlist, so anything not matched
   is silently absent rather than loudly missing.

   ```sh
   npm pack --dry-run --workspace=@gaborwnuk/axs-core
   ```

4. **Publish.** The package is scoped, and scoped packages default to
   restricted; `publishConfig.access` in `package.json` already forces public,
   so no access flag is needed. The account has 2FA enforced for writes, so a
   one-time code is:

   ```sh
   npm publish --workspace=@gaborwnuk/axs-core --otp=123456
   ```

   Without `--otp` this fails with:

   ```
   npm error code E403
   npm error 403 Two-factor authentication or granular access token with
   npm error 403 bypass 2fa enabled is required to publish packages.
   ```

   Being logged in is not sufficient — `npm whoami` succeeding only proves the
   stored credential identifies you, not that it may publish. If `--otp` is
   still rejected, the stored token is a granular one without publish rights;
   re-authenticate with `npm logout && npm login` and retry.

   The alternative npm suggests — a granular token with *bypass 2FA* — is
   deliberately not used here: it is a standing publish credential on disk, and
   it expires every 90 days, which is what ruled out automated publishing in the
   first place.

   **The `--workspace` flag is required.** Running plain `npm publish` from the
   repository root targets the root package, `sram-axs-workspace`, which is
   `"private": true` and fails with:

   ```
   npm error code EPRIVATE
   npm error This package has been marked as private
   ```

   That is the guard working as intended — the root exists only to hold the
   workspaces and must never reach the registry. Do not remove its `private`
   field; pass `--workspace`, or `cd packages/axs-core` and publish from there.

   If npm rejects this with a provenance error instead, check that
   `publishConfig.provenance` has not been reintroduced — provenance can only be
   generated by a supported CI with OIDC, never from a laptop.

5. **Tag and push.** This triggers the GitHub release.

   ```sh
   git commit -am "release: axs-core <version>"
   git tag v<version>
   git push origin main --tags
   ```

## Notes

- **Publish before tagging**, so a GitHub release never advertises a version
  that failed to reach npm.
- **npm publishes are effectively permanent.** Unpublishing is restricted to a
  72-hour window and only when nothing depends on the package; after that the
  only remedy is `npm deprecate` and a new version.
- The version lives in `packages/axs-core/package.json`. The root workspace is
  private and its version is not published.
